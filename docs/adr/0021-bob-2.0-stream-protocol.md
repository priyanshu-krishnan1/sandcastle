# Bob-Shell 2.0's real `stream-json` event vocabulary

## Context

The `bob` **agent provider**'s `parseStreamLine` was originally written against an
assumed event shape (`{"type":"tool_call",...}`, `{"type":"session_id",...}`) that
does not match what `bob run --format stream-json` actually emits. IBM's docs for
Bob-Shell 2.0 confirm the real vocabulary is:

```
{"type":"message","role":...,"content":"...","isReasoning":bool}
{"type":"tool_use","tool_name":"...","tool_id":"...","parameters":{...}}
{"type":"tool_result","tool_id":"...","status":"...","output"|"error":"..."}
{"type":"error","severity":"...","message":"..."}
{"type":"result","status":"success"|"error","last_message":"...","stats":{...}}
```

`parseBobStreamLine`'s fallback for any line that isn't recognized JSON is to treat
it as plain text (`{type:"text",...}`), which feeds `onText`/`accumulatedOutput` —
the exact buffer Orchestrator.ts scans for the **completion signal**
(`<promise>COMPLETE</promise>`). Against the assumed schema this fallback was doing
most of the work: `tool_use`/`tool_result`-shaped events, the `message` role-echo of
the prompt, and reasoning content were all falling through to plain text. That is a
real hazard, not a theoretical one — a `tool_use` event's `parameters` routinely
contains file contents or shell arguments, a `tool_result`'s `output` routinely
contains grep/cat output, and either can trivially contain the literal completion
signal string (e.g. a tool call that writes or greps for a prompt file containing
the instruction that tells the agent when to emit it). Letting any of that reach the
text-scanning path would let the signal fire on data the agent never asserted as its
own completion — a false positive that reports an iteration (and any phase gated on
it) as done when the actual task wasn't finished or verified.

The `message` event carries the same hazard from a different direction: Bob-Shell
echoes the caller's own prompt back on the stream as a `role: "user"` message, and
the prompt text itself routinely contains the literal signal (it's the instruction
telling the agent when to emit it). Treating a `message` event as text without
checking `role` would let the echoed prompt trigger the signal before the agent had
said anything.

## Decision

`parseBobStreamLine` now special-cases every event type in the real vocabulary
before the generic plain-text fallback runs, so each one is routed to the channel
that matches what it actually is:

- `{"type":"message","role":"assistant","isReasoning":true}` → dropped entirely
  (`[]`). Reasoning/chain-of-thought commentary can plausibly mention or quote the
  completion signal without the agent asserting completion.
- `{"type":"message","role":"assistant","content":string}` → `{type:"text",...}`.
  This is the only case that reaches the completion-signal-eligible text channel.
- `{"type":"message"}` with any other role (e.g. `"user"`, the prompt echo) →
  dropped entirely.
- `{"type":"tool_use","tool_name":...}` → `{type:"tool_call", name: tool_name, args:
  JSON.stringify(parameters)}`. Routed through `onToolCall`, never `onText`.
- `{"type":"tool_result",...}` → `{type:"tool_call", name:"tool_result", args:
  output ?? error ?? ""}`. Same channel, same reasoning.
- Top-level `{"type":"error",...}` → `{type:"tool_call", name:"error", args:
  message}`. Deliberately not treated as assistant text even though "error" reads
  like a message — kept visible for debugging via the tool-call channel without ever
  being eligible for signal matching.
- `{"type":"result","status":"success",...}` with `last_message`/`result` text →
  emits `{type:"text",...}` **and** `{type:"result",...}` (plus a `usage` event if
  `stats` is present). This is the one place a `result` event is allowed to reach
  the text channel, because it carries the agent's own final message.
- `{"type":"result","status":"success",...}` with **no** text content → emits only
  the `usage` event, nothing else. This is a deliberate refusal to fabricate a
  completion: a bare successful process/turn exit is not the same claim as the agent
  asserting `<promise>COMPLETE</promise>`, and conflating them would let a stray
  backgrounded child or an agent simply running out of things to do this turn look
  identical to genuine completion.
- `{"type":"result","status":"error",...}` → `{type:"tool_call", name:"error",...}`
  (plus `usage` if present). Orchestrator.ts's exit-code path is what actually fails
  the run; this only keeps the failure visible without ever counting as a text
  message.
- Two legacy/defensive cases are kept as harmless additional matches for other
  Bob-Shell versions: an assumed 1.x-shaped `{"type":"tool_call",...}` (Bob 2.0 uses
  `tool_use`/`tool_result` instead) and an assumed `{"type":"session_id",...}` (Bob
  2.0's real protocol has no such event at all — see the dedicated section below).
- Anything else — a line that isn't JSON, or a parsed JSON object whose `type`
  doesn't match any of the above — still falls through to the plain-text default.
  This is an intentional forward-compatibility choice (an unrecognized event
  shouldn't be silently swallowed), but it means a genuinely new Bob event type
  introduced by a future Bob-Shell release would reach the signal-scanning path
  until this file is updated for it. See Consequences.

Alongside the event-mapping fix, `BobOptions` gained optional fields mapping to
`bob run` flags that previously had no way to be set: `maxTurns` (`--max-turns`),
`maxCost` (`--max-cost`), `disableToolGroups` (`--disable-tool-groups <a,b,...>`),
`disableMcp` (`--disable-mcp`), `disableSubagents` (`--disable-subagents`),
`workspace` (`--workspace <path>`), `trust` (`--trust`), and `acceptLicense`
(`--accept-license`). All of these are omitted from the command line unless set,
**except** `trust` and `acceptLicense`, which default to `true` — bob runs headless
in an ephemeral/remote sandbox with no human to answer a first-run trust or license
prompt, and an unanswered prompt would otherwise hang until the idle timeout. The
existing `model` field's doc comment was corrected in the same pass: it renders as
`bob run`'s `--mode` flag (both in `buildPrintCommand` and `buildInteractiveArgs`),
not `--model` — Bob 2.0's `run` command has no `--model` flag. The field name itself
is kept for backwards compatibility with the positional `model` argument on `bob()`.

### Why `bob` still does not declare `sessionStorage`

None of the above adds an `AgentSessionStorage` for `bob`, and that is deliberate,
not an oversight. Per [ADR 0012](./0012-agent-provider-owned-session-storage.md),
resumability is an opt-in sub-object an `AgentProvider` declares when it owns a
session record Sandcastle can transfer host↔sandbox; per
[ADR 0016](./0016-resume-requires-filesystem-backed-sessions.md), that record must
be filesystem-backed — a discrete file (or set of files) per session Sandcastle can
read/copy/rewrite as opaque content. Bob's own resume mechanism is `bob run --resume
<task-id>` (or `--resume latest`) against what is, in Sandcastle's usage, a
remote/ephemeral host — a server-side task identifier, not a session file that lives
on disk where Sandcastle can capture it after the run and feed it back in before the
next one. That puts `bob` in the same non-resumable category ADR 0016 already
carves out for OpenCode's SQLite store: a real session concept exists, but it isn't
one Sandcastle's file-transfer model can reach.

`AgentCommandOptions.resumeSession` is still threaded into `buildPrintCommand` and
rendered as `--resume <task-id>` when set. This is not dead code and not a
contradiction of the above — it is a no-op today because nothing sets
`resumeSession` for a provider with no `sessionStorage` (the ADR 0012 mechanism
never populates it). It exists so that a future **remote-native** `AgentSessionStorage`
implementation — one that stores a task id instead of a JSONL file, distinct from
ADR 0012's filesystem-backed shape — has a CLI seam to plug into without another
round of protocol changes to `buildPrintCommand`. Building that implementation is
out of scope here; this ADR only records that the plumbing was left in place on
purpose.

## Consequences

- `RunResult.resume()` and `RunResult.fork()` remain typed `never` for `bob()`
  results today, via the existing ADR 0012 mechanism (no `sessionStorage` declared).
  Nothing in this change enables resume or fork for bob.
- `captureSessions` stays `false` for `bob`, unchanged.
- The new budget/permission-shaping flags (`maxTurns`, `maxCost`,
  `disableToolGroups`, `disableMcp`, `disableSubagents`, `workspace`) are opt-in and
  omitted from the command line unless a caller sets them, so existing `bob(...)`
  callers see an unchanged command line and unchanged behavior.
- `trust` and `acceptLicense` are the exception: they now default to `true` and are
  always appended (`--trust --accept-license`) unless a caller explicitly passes
  `false`. This is a deliberate behavior change from "unset" to "always trust,
  always accept" for every existing caller, made to prevent headless runs from
  hanging on an unanswerable prompt; a caller that wants the interactive prompt back
  must opt out explicitly.
- The event-mapping fix closes the specific false-completion hazard described above
  for every event type Bob-Shell 2.0's documented vocabulary defines. It does not
  close it for undocumented/future event types: an unrecognized `{"type":"..."}`
  object still falls through to the plain-text default and is eligible for
  completion-signal matching. That residual gap is accepted as the cost of not
  silently dropping genuinely new events; closing it fully would require Bob-Shell
  to document (or Sandcastle to allowlist) its complete event vocabulary.
